# 04 — Human Resources

> **Scope.** Workforce roll-forward by cost centre, hiring/dismissal/attrition,
> productivity indices I and II (the learning curve), motivation, absenteeism,
> training, process optimisation, the social plan, and overtime accounting.

---

## 1. Cost centres

Five fixed cost centres, each with its own workforce balance:

| Cost centre        | Driven by                                                                |
|--------------------|---------------------------------------------------------------------------|
| **Purchasing**     | Auto-scaled to revenue (and complexity — see §5)                          |
| **Administration** | Auto-scaled to revenue                                                    |
| **Production**     | Team decision: `hr.production_workforce_change` (positive = hires, negative = dismissals) |
| **R & D**          | Team decision: `rnd.by_product[*].researchers` (engine reconciles total) |
| **Sales**          | Team decision: `sales.by_product[*].by_market[*].sales_force` (engine reconciles total) |

A team **does not** set Purchasing or Administration headcounts directly —
those follow revenue, with the engine hiring/firing automatically. The team
*does* pay the resulting hiring/dismissal costs.

---

## 2. Workforce roll-forward

For each cost centre *c*:

```
opening(c, t)   = closing(c, t-1)
hires(c, t)     = explicit_hires(c, t)    + auto_hires(c, t)
dismissals(c, t)= explicit_dismissals(c, t) + auto_dismissals(c, t)
attrition(c, t) = opening(c, t) · attrition_rate(c, t)

closing(c, t)   = opening(c, t) + hires(c, t) − dismissals(c, t) − attrition(c, t)
```

### 2.1 Attrition

```
attrition_rate(c, t) = A_base
                    · (non_salary_pct_min / non_salary_pct(t))       // pay more, lose fewer
                    · (motivation_ref / motivation_index(t))         // motivate, retain
```

Defaults: `A_base = 0.04` (4 % baseline attrition), `motivation_ref = 100`.

The non-salary-cost lever lets teams trade present cash for lower attrition;
the motivation lever lets them trade soft investments (training, process
opt, image) for the same.

### 2.2 Hiring and dismissal costs

```
hiring_costs = hires(c, t) · hiring_cost_per_head
dismissal_costs_base = dismissals(c, t) · dismissal_cost_per_head
dismissal_costs_social_plan = social_plan_surcharge(c, t)
```

Hiring cost default: 12 500 EUR/head. Base dismissal cost default: 10 000
EUR/head.

### 2.3 Social plan

When dismissals in a single cost centre exceed thresholds, a regulatory
"social plan" surcharge applies (in some scenarios negotiated with a workers'
council). Cumulative — the highest applicable threshold's rate applies to
*all* dismissals that period:

| Threshold (% of opening) | Extra fee per dismissal |
|--------------------------|--------------------------|
| 10 %                     | 15 000 EUR               |
| 30 %                     | 20 000 EUR               |
| 50 %                     | 25 000 EUR               |

So a dismissal of 35 % of production headcount incurs the 20 000 EUR
surcharge on *every* dismissal, not just on those above the threshold.

### 2.4 Reshuffles

Moves *within* a cost centre (e.g., a sales rep reassigned from market 1 to
market 2, or a researcher moved from product A to product B) are **not**
hires or dismissals. The engine recognises this by computing
hires/dismissals as the net change in cost-centre headcount, not the sum of
per-allocation changes.

## 3. Production-staff specifics

The production cost centre is where the productivity machinery lives.

### 3.1 Staff productivity (units per staff-period)

Base productivity is a scenario constant per product: how many finished
units one production worker produces in one period, with all indices at 100.
For `solar-v1`, `production_capacity_per_person = 50` (units/period) for
`panel_gen1`.

Actual productivity is base × index I × index II (§4 below).

### 3.2 Staff required

```
staff_required(p) = production_volume(p)
                  / ( base_productivity(p) · index_I · index_II )
```

Compared to *available staff* (= production headcount × (1 − absenteeism)):

```
available_staff = production_headcount · (1 − absenteeism_rate)
```

If `staff_required > available_staff`, the engine schedules overtime up to
`overtime_max_pct` (see `03-production.md` §2.3). Beyond that, production is
staff-bound (units produced < target).

## 4. Productivity indices

Two multiplicative factors. Both start at 1.00 in period 0.

### 4.1 Productivity Index I — within-period factors

```
index_I = process_optimisation_index
        · adaptation_index
        · competence_index
        · motivation_index
```

Each component is centred at 1.00; values above raise productivity, below
drop it. All four evolve period-to-period:

#### 4.1.1 Process-optimisation index

```
process_optimisation_index(t) = max(0.8,
    process_optimisation_index(t-1) · (1 − decay_proc)
    + P_K · log(1 + process_optimisation_spend(t) / P_ref)
)
```

Defaults: `decay_proc = 0.02`, `P_K = 0.05`, `P_ref = 2 500 000 EUR`.

#### 4.1.2 Competence index — from training

```
competence_index(t) = max(0.8,
    competence_index(t-1) · (1 − decay_comp)
    + C_K · log(1 + training_per_employee(t) / C_ref)
)
```

Defaults: `decay_comp = 0.02`, `C_K = 0.04`, `C_ref = 1 600 EUR/employee`.

Training is decided as *euros per employee* (default budget guidance: 2–4
training days × 800 EUR/day in industry-standard pricing).

#### 4.1.3 Motivation index — slow-moving, multi-driver

```
Δmotivation = (
    + μ_util  · (staff_utilisation − 1)
    + μ_image · (image_index − 100) / 100
    − μ_growth · |Δ workforce / opening|              // sudden growth or shrink hurts
    + μ_nsc   · (non_salary_pct − non_salary_pct_min)
    + μ_pens  · pension_reserve_pct
    + μ_proc  · (process_optimisation_index − 1)
    + μ_train · (competence_index − 1)
    + μ_qly   · (efficiency_index − 100) / 100
)
motivation_index(t) = clip(motivation_index(t-1) + σ_mot · Δmotivation, 50, 150)
```

Defaults all = 1.0 (each driver weighted equally), `σ_mot = 5` (smoothing).
Staff utilisation around 98 % is optimal — both under-utilisation
(slack) and over-utilisation (burnout) hurt motivation.

#### 4.1.4 Adaptation index — orientation cost of new hires

New hires take a period to ramp up. Each period, the adaptation index is:

```
adaptation_index = 1 − A_K · (hires(production) / opening(production))
```

Defaults: `A_K = 0.5`. So hiring 10 % of opening workforce drops adaptation
by 5 %.

This is a *within-period* drag — the period after a big hiring wave, the
new hires are no longer "new" and adaptation snaps back.

### 4.2 Productivity Index II — the learning curve

```
index_II(t) = index_II(t-1) · (1 + L_K · log(1 + Δ_cumulative_units / cumulative_units(t-1)))
```

Where `Δ_cumulative_units` is the units produced this period, and
`cumulative_units` is the running total of all units of the same product
ever produced by this company.

`L_K` is the *learning-rate coefficient*. We use a logarithmic form
equivalent to Wright's learning curve (sources §4):

> Per-unit cost (here: per-unit labour) declines by a fixed % with every
> doubling of cumulative output.

Defaults: `L_K = 0.07` → about 4.9 % productivity gain per doubling. This
corresponds to an 85 % learning rate, midway in the industry-typical
75–90 % range for assembly operations.

### 4.3 Combined actual productivity

```
actual_productivity(p) = base_productivity(p) · index_I · index_II
```

For `panel_gen1` with `base = 50`, `index_I = 1.05`, `index_II = 1.03`:
actual = 50 × 1.05 × 1.03 = 54.075 units/staff/period.

## 5. Auto-scaled cost centres (purchasing, administration)

These two cost centres do not have a team-controlled headcount. Their
headcount auto-scales with the company's revenue per period, using a
scenario-defined piecewise-linear schedule:

```yaml
hr.cost_centres.purchasing.headcount_by_revenue:
  - { revenue_mEUR: 25,  headcount: 6  }
  - { revenue_mEUR: 50,  headcount: 10 }
  - { revenue_mEUR: 100, headcount: 16 }
  - { revenue_mEUR: 150, headcount: 20 }
  # interpolated linearly between rows; clipped outside
```

Purchasing additionally scales with **product complexity**: a higher
efficiency index means more complex products and more procurement work.
A multiplicative bump:

```
purchasing_headcount = base_schedule(revenue) · (1 + π_complex · (max_eff_index − 100) / 100)
```

Default `π_complex = 0.5`.

When auto-scaling triggers a hire or dismissal, the standard
hiring/dismissal costs apply (no social-plan surcharge for these auto-moves
unless they exceed the same thresholds).

## 6. Absenteeism

A rate by which available staff is reduced from headcount:

```
absenteeism_rate = max(0,
    B_base
    + β_mot   · (motivation_ref − motivation_index) / motivation_ref
    + β_proc  · max(0, process_optimisation_index − 1.05)    // over-pressure
    + β_growth · max(0, Δ workforce / opening − 0.05)        // rapid growth
    + β_env   · max(0, environmental_compliance_baseline − env_damage_indicator) / 100
    − β_nsc   · (non_salary_pct − non_salary_pct_min)
    − β_train · (competence_index − 1)
)
```

Defaults: `B_base = 0.03`, all `β` = 0.05. Bounded at 0 below and at 0.25
above (a 25 % absenteeism rate would be a wildcat strike).

---

## 7. Overtime accounting

When overtime is scheduled (`03-production.md` §2.3):

- Step fixed cost added once per period in the production cost centre.
- Wage premium = `overtime_wage_premium_pct × (overtime_hours / regular_hours)
  × wages_production`. This is added as a **separate line** in cost-type
  accounting, not buried in regular wages, so the team can see it.
- The premium is **not** in the personnel report's headline workforce
  number; it's a wage adjustment.
